# Axiom 0.95.0

**Released:** 17 November 2026

## Release validation record, signing decision, and the ILLink investigation

This release is documentation and validation; no product code changed.

### New validation record

[docs/validation/RELEASE_VALIDATION_2026-11-17.md](../validation/RELEASE_VALIDATION_2026-11-17.md)
records:

- In-place upgrades on the host and the isolated VM from 0.89.0 through 0.94.0: setup exit code,
  `install.json`, desktop/service binary versions, service state, Blackbox marker, enforcement
  status and the SYSTEM-only policy ACL, UpgradeDataGuard counts, Privacy Shield entries and the
  DKG node coming up on 0.93/0.94.
- What was **not** run: a pristine-OS image install, the interactive wizard, and the WFP OS-deny

  window).
- The signing decision: SignPath Foundation Authenticode signing through GitHub OIDC, Azure Trusted
  Signing as fallback, no self-signed certificates and no keys in the repository; artifacts stay
  explicitly unsigned until enrollment.
- Cross-platform ports remain open and cannot be validated on the Windows-only runner.

### NU1009 / ILLink: why the pin stays

The .NET 10 SDK adds `Microsoft.NET.ILLink.Tasks` implicitly for trimmed publishes, and Central
Package Management needs the pin that was in place. Removing the explicit references and the pin
does remove the publish-time "delete explicit package reference" warning, but the implicit version
follows the SDK patch: a lock file generated on SDK 10.0.403 (ILLink 10.0.14) fails locked restore
on the runner's newer 10.0.4xx SDK (ILLink 10.0.15, `NU1004`). That breaks the CI integrity gate for
a cosmetic warning.

- The explicit references and the `Microsoft.NET.ILLink.Tasks` pin are kept.
- The publish warning is accepted and documented; it does not affect the artifacts.
- A future fix needs either a pinned SDK image or an SDK property that makes the implicit package
  version deterministic; both are tracked with the release-engineering work, not forced through a
  lock-file bypass.
