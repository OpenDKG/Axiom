# Axiom 0.8.1

**Release date:** 2026-11-09

Axiom 0.8.1 is a post-reboot fix release for the 0.8.0 installation. It corrects the notification-area
icon, the module console windows that stayed visible, the startup order between core protection and
the optional modules, and the Privacy Shield memory growth in the Axiom service.

## Fixes

### Tray icon

- A `TrayIcon` created in code stays detached until it belongs to the application's `TrayIcons`
  collection, and a detached icon is never registered with the shell. Axiom therefore ran in the
  background with no icon next to the clock and no error to notice.
- The icon is now attached after the window shows and detached on exit. A shell failure is logged to
  `%LOCALAPPDATA%\Axiom\tray-error.log`, and close-to-tray is disabled so the app is never stranded
  without a way to reopen it.

### Module console windows

- The Blackbox installer starts its DKG node and dashboard from its own login tasks, so those
  `node.exe` consoles are not descendants of the Axiom desktop process and the existing hider never
  saw them.
- The new module hider matches the Axiom and Blackbox module command lines, including
  `%LOCALAPPDATA%\hermes\blackbox` and `%LOCALAPPDATA%\Axiom\modules\...`, and hides their top-level
  window. An unrelated user Node.js window is never touched; console windows stay hidden for later
  module starts as well.

### Startup order

- The 43 MB Privacy Shield ruleset is loaded on a background task instead of the service constructor.
  The service pipe, the persisted firewall consent and the monitor are available while the optional
  DKG and Blackbox modules are still loading.
- Measured cold start on the installed service: the process runs after 0.5 s and the loopback
  resolver answers after 3.9 s, with 212 MB working set at the first answer.

### Service memory

- The compiled DNS policy (about 190 MB of managed objects for 300,000 domains) is built once and
  reused until the settings or the ruleset change. A status poll no longer rebuilds it, which was the
  source of the repeated working-set spikes toward 1.6 GB.
- Sources totals are cached when the ruleset is adopted instead of being recomputed by scanning every
  rule per source on each status request.
- The ruleset is streamed from disk rather than read into a 43 MB string, and the large object heap is
  compacted once after the startup load so the memory returns to the OS.
- Idle usage after the change measured 230-285 MB working set (190-225 MB private) and stayed flat
  while the desktop polled status.

## Scope notes

- The DKG and Blackbox `node.exe` workers are separate processes and their several hundred MB is not
  part of the Axiom service footprint.
- Task Manager groups processes by executable, so `Axiom.Service.exe` and the module `node.exe`
  workers cannot be folded into the `Axiom.Desktop.exe` group. Axiom cannot change that grouping.
- Version 0.8.1 changes no firewall, DNS, privacy or installer behaviour from 0.8.0.

## Verification

- `dotnet build Axiom.sln`: 0 warnings, 0 errors.
- `dotnet test Axiom.sln`: 435 passed, 0 failed, including a new regression test that repeated status
  polls keep the per-source totals from the cached index.
- Installed desktop and service rebuilt from this source and restarted on Windows 11:
  - `Shell_NotifyIconGetRect` returns the icon rectangle inside the taskbar, so the tray icon is
    registered rather than missing;
  - the resolver answers on `127.0.0.1:53` (blocked domain returns NXDOMAIN, a normal name resolves);
  - every Axiom and Blackbox `node.exe` reports `MainWindowHandle = 0`;
  - service memory stayed flat over repeated status polls.

## Known limitations

- ETW telemetry is not integrated yet. SNI, TLS certificate subjects, DNS query names, exact
  per-connection byte counts and TIME_WAIT ownership remain missing evidence.
- No reputation or threat-intelligence feed is configured; Axiom does not invent a score.
- Traffic totals cover TCP only, measured from Windows extended TCP statistics; UDP is not measured.
