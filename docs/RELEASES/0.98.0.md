# Axiom 0.98.0

**Released:** 17 November 2026

## Export the Axiom-owned firewall rules (FND-008, export half)

The Network Control page lists the rules Axiom owns, but there was no way to take that list out of
the app for review, an audit trail or a migration. The Owned rules header now has **Export rules**,
which writes a JSON file through the native save dialog.

The export is read-only and deliberately narrow:

- Only Axiom-owned rules are included; unrelated Windows Firewall rules are never read into the
  file.
- It carries the durable intent (application path, direction, action, profiles, protocol, remote
  addresses/ports, enabled, description, creator, schema version) and the current OS state
  (`managedRuleId`, OS rule name, state, last verified time, last error code).
- No secrets, tokens, raw exceptions or machine identifiers are added.
- Export never applies, imports or changes a rule. Import remains open in FND-008 and needs a
  preview plus validation path before it can be safe.

File shape:

```json
{
  "schema": "axiom.firewall-rules.v1",
  "exportedAtUtc": "2026-11-17T06:30:00.0000000+00:00",
  "rules": [
    {
      "managedRuleId": "…",
      "osRuleName": "Axiom::…::OUT",
      "state": "Applied",
      "appPath": "C:\\Apps\\agent.exe",
      "direction": "Outbound",
      "action": "Block",
      "profiles": "Private, Public",
      "protocol": "Tcp",
      "remoteAddresses": ["1.1.1.1"],
      "remotePorts": "443",
      "enabled": true,
      "createdBy": "AXIOM\\lab",
      "schemaVersion": 1
    }
  ]
}
```

With no owned rules the command reports "No Axiom-owned rules to export." instead of writing an
empty file.

## Verification

- `dotnet build Axiom.sln -c Release` — 0 warnings, 0 errors.
- New `FirewallRuleExportTests`: the schema, the exported fields, the empty-list case.
- Windows CI build, tests and packaging check pass; 0.98.0 installed on host and in the VM.

## Not in this release

Import/validation of a rule file (FND-008) stays open; so do the other FND items and the remaining
reboot-recovery gap for the vendor DKG node (#315).
