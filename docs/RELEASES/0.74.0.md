# Axiom 0.74.0

**Released:** 16 November 2026

## OS enforcement policy

Axiom now provisions the opt-in enforcement policy the local service reads (issue #403).

Before this release `%ProgramData%\Axiom\enforcement-policy.json` was never written by anything, so
`enforcement.status` reported `enabled=false`, zero agents, zero rules and zero protected resources —
a firewall page with no policy and no receipts, while the hook guard still blocked. The file is
machine scope because the service runs as LocalSystem and cannot read a per-user profile.

- New `EnforcementPolicyProvisioner` writes a conservative default: the eleven supported harnesses
  run in `protectSelectedOperations`, and agent reads/writes/deletes under `.ssh`, `.aws`, `.kube`,
  `.gnupg`, `.git-credentials`, `.npmrc`, `Microsoft\Credentials` and the Chrome profile are blocked.
- The installer writes it once (elevated); an existing operator policy is never overwritten. The
  desktop start also tries, and silently skips when it lacks the elevation.
- Verified after install: `enforcement.status` returns `enabled=true`, 11 agents, 88 rules,
  8 protected resources.

## Notes

- The policy governs the enforcement/receipt layer, not Windows Firewall rules: Axiom-owned firewall
  rules still come from explicit rule decisions on the Firewall page.
- The pinned Blackbox DKG node on the lab VM is still unhealthy (`promote-worker: table index is out
  of bounds`, `.blackbox-store-reset-pending`), so the dashboard shows `NODE OFFLINE`; the compiled
  ruleset (1,109,000 verified rules) keeps enforcing.

## Verification

- `dotnet build Axiom.sln -c Release` — 0 warnings, 0 errors; full suite green before packaging.
- Installed in the lab VM silently after publishing; `enforcement.status` and the dashboard graph
  re-checked on the installed build.
