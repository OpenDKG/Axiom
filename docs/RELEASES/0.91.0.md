# Axiom 0.91.0

**Released:** 17 November 2026

## Row context menus copy again (issue #296)

0.90 disabled the ScrollViewer's built-in scroll menu, and VM verification showed the row menu
(Copy event / Copy details / Copy raw event JSON) now opening over the selected row. The copy
commands still did nothing: their bindings read
`$parent[ContextMenu].PlacementTarget.Tag...`, and in Avalonia 12 a pointer-opened menu leaves
`ContextMenu.PlacementTarget` null. The framework sets the placement target on the popup, not on
the menu. Every binding that went through it resolved to null, which is exactly the second symptom
in #296: the menu opens, the clipboard stays unchanged.

- A class handler in `ContextMenuPlacement` restores the owning control on the menu after the
  framework opens it, so the existing `PlacementTarget.Tag...` bindings resolve again. This fixes
  the menu actions in every list and row view (activity, findings, connections, apps, events,
  firewall, privacy, agent health), not only the dashboard.
- The Agent Dashboard and Agent Activity menus are also attached to the `ListBox` itself now and
  bind to its DataContext, so they do not depend on the placement target at all.
- 0.90's `ScrollViewer.ContextMenu = null` style stays, so the scroll menu cannot win the lookup.

## Verification

- `dotnet build Axiom.sln -c Release` — 0 warnings, 0 errors.
- New UI tests: a pointer-opened menu exposes its owner as `PlacementTarget` and its item command
  binding resolves; right-clicking an activity row opens the menu, its copy command runs, and the
  clipboard receives the selected row.
- VM, installed 0.91.0, UI Automation: right-click a row → `context_menu=OPEN` with
  `Copy event / Copy details / Copy raw event JSON`, the row is selected, and `Copy event` fills
  the clipboard.
