# Axiom 0.10.7

**Release date:** 2026-11-10

Security hardening for the Windows service, machine-wide state and DNS handling, plus a fix for
replacing the protected service image. The findings come from an independent review of v0.7.6 and
were re-verified against current main.

## Service image (critical)

- The LocalSystem service is now copied to `%ProgramFiles%\Axiom\Service` by the elevated installer,
  with a SYSTEM/Administrators-only ACL and no user write access. Previously it lived in
  `%LOCALAPPDATA%\Programs\Axiom`, where any process of the signed-in user could replace it and run
  code as SYSTEM after a restart.
- The copy is verified by SHA-256 before the service registration is pointed at it, and the
  registration is updated even when the service already exists.
- An older install is repaired from the service itself on the next start: it copies its running
  image to the protected directory and re-points the registration.
- The installer now waits for a pending stop and retries the image copy, instead of failing with
  exit code 7 while Windows still has the old image mapped.

## Machine-wide state (high)

- `%ProgramData%\Axiom` is created or repaired as SYSTEM and Administrators only, with inheritance
  removed and no user create permission. This closes both the planted-directory junction and the
  pre-created `protection.json.tmp` race.
- Settings are written through a randomly named temp file, and a temp file is deleted on failure.
- The legacy migration refuses a source or destination that is a junction or symbolic link.
- The database and settings are no longer readable by other local users.

## DNS handling

- The elevated restore no longer applies the per-user backup. It reads only the machine snapshot,
  rejects a reparse point or a file not owned by SYSTEM/Administrators, and accepts only parsed IP
  addresses. The per-user JSON stays a UI convenience and is not trusted by an elevated process.
- The SYSTEM failsafe validates the same way. If the snapshot is missing, untrusted or incomplete,
  it resets the affected adapters to DHCP instead of leaving them on a dead resolver.
- The resolver drops an upstream reply whose transaction id or question does not match the query
  and tries the next upstream.

## Smaller items

- The local pipe rejects Inbound + Allow rule specs, even for the allowed user.
- The community feed has a 2 MB body cap.
- The agent-lockdown hint now says it covers the exact detected executables, not renamed copies or
  other tools.
- The documented Blackbox one-liner uses `https://`.

## Upgrade note

Existing installations keep working. The next time Shield is enabled or repaired, Windows asks for
elevation once and the service moves to `%ProgramFiles%`. Starting the updated service also repairs
the path automatically. No firewall rules are changed by the move.

## Verification

- `dotnet build Axiom.sln -c Release`: 0 warnings, 0 errors.
- `dotnet test Axiom.sln -c Release --no-build`: 490 passed, 0 failed.
- Local install: `sc qc Axiom` reports `C:\Program Files\Axiom\Service\Axiom.Service.exe`; the
  service starts and answers on the pipe.
- The standard user is denied access to `%ProgramData%\Axiom` and to the service directory.
- With Ethernet DNS forced to `127.0.0.1` and a valid machine snapshot, stopping the service
  restored `192.168.0.1`; the resolver restarted and blocking worked again.
- Dark and light themes checked for the About/Privacy pages after the change; no UI regression.

## Still open

- Full same-user pipe authentication needs signed binaries and an image check or a secure desktop.
- Agent hooks still fail open by design; that is a separate behaviour decision.
- Binaries are not Authenticode-signed yet.
- History write batching (SSD wear) is a separate change under review; it is not part of this
  version.
