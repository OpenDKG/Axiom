# Axiom 0.10.21

**Release date:** 2026-11-11

The DKG installer now pins the release that matches the network it initialises, installs it from a
lockfile, and turns off the node's own updater.

## What was wrong

`OptionalModuleInstaller` ran `npm install @origintrail-official/dkg@latest` and then
`dkg init --network testnet`. On npm, `latest` is the **mainnet** build (10.0.27 at the time of
writing) while testnet is 10.1.0, so Axiom initialised a mainnet build against testnet. The
generated `package.json` also used a caret range (`^10.0.27`), and the node's own
`autoUpdate.enabled=true` replaced whatever was installed from the testnet channel every five
minutes. The version that Axiom checked was not the version that ran.

## What changed

- `DkgRelease` pins `@origintrail-official/dkg@10.1.0` and network `testnet`.
- A committed `package.json` and `package-lock.json` are embedded in `Axiom.Presentation` and
  written to the install root. The installer runs `npm ci --ignore-scripts` instead of
  `npm install @latest`, which fixes transitive dependencies as well.
- The script reads the installed package version, stops an existing Axiom-managed node when the
  version differs, upgrades it, rebuilds `better-sqlite3`, and only then runs `dkg init`.
- After a successful init, the installer sets `autoUpdate.enabled=false` in
  `DKG_HOME\config.json`. Updates now require an Axiom release.
- The DKG status line includes `networkName` from `/api/status` alongside version, peer and role,
  so a mismatch is visible in the module card.
- `package.json`, `package-lock.json` and the installer version are kept in sync by a test that
  reads the embedded resources.

## Limits

- The lockfile is generated from npm's public registry and pins the package tree as published; a
  future security update needs a new Axiom release and lockfile, by design.
- A DKG installation created outside Axiom (global npm) is not modified. Its auto-update setting
  and version remain the user's responsibility.
- This is a version/network fix only. Running two DKG nodes on one port and accepting any HTTP
  listener on 9200 are tracked separately (#226, #227).

## Verification

- `dotnet build Axiom.sln -c Release`: 0 warnings, 0 errors.
- `dotnet test Axiom.sln -c Release`: 554 passed, 0 failed. New tests check the embedded manifest
  and lockfile pin 10.1.0 and target testnet, and the status parser reports the network name.
- Local check: the existing Axiom-managed install was 10.0.27 from npm `latest`; the new script
  detects that and upgrades to 10.1.0. No DKG process was stopped or reinstalled during the build.
- DKG auto-update was confirmed enabled in the current `DKG_HOME\config.json`
  (`"enabled": true, "source": "npm"`); the installer now writes `enabled: false`.
