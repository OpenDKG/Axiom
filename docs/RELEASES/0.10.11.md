# Axiom 0.10.11

**Release date:** 2026-11-10

Axiom Shield no longer asks again about an application just because an update moved it to a new
version folder.

## What was happening

Decisions were saved correctly — the service held 34 allow/block decisions across restarts — but
they were matched by the **exact executable path**. Many installers change that path on update:

- `...\GoogleUpdater\157.0.8089.0\updater.exe` becomes `158.x\updater.exe`
- `...\OpenAI\Codex\bin\f71a721e0e6193a9\codex.exe` gets a new hash folder
- WindowsApps packages change the version and publisher hash in the folder name

Each new path looked like a new application, so the ask queue showed something the user had already
decided.

## What changed

- A **path family** key ignores version segments (`157.0.8089.0`), hash segments (16+ hex characters)
  and WindowsApps package segments (`_x64__`, `_arm64__`, `_x86__`) while keeping the executable
  name and the rest of the path.
- The ask-queue detector treats an application as decided when either the exact path or its family
  has a decision.
- The service reconciles new paths every five seconds: an inherited **allow** is recorded without a
  prompt, and an inherited **block** also creates the outbound firewall rule for the new path before
  recording it.
- The most recent decision in a family wins, so changing “allow” to “block” still applies.

## Safety notes

- The family only replaces a single path segment; a different executable name or a different parent
  chain is not matched. A malicious file placed in the same versioned folder with the same name
  would inherit the decision — the same exposure as the old per-file rule, but without a prompt.
- Unsigned applications in unrelated folders are still asked separately.

## Verification

- `dotnet build Axiom.sln -c Release`: 0 warnings, 0 errors.
- `dotnet test Axiom.sln -c Release --no-build`: 500 passed, 0 failed.
- New tests: version, hash and WindowsApps folders normalize to the same family; an ordinary path is
  unchanged; a decision for version 157 suppresses the prompt for 158 while a genuinely new path is
  still listed.
- Live status before the change: 34 decisions and 21 pending; none of the pending paths were in the
  decisions, which confirms the stored decisions were intact and only the matching was wrong.
