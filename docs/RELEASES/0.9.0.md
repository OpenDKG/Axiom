# Axiom 0.9.0

**Release date:** 2026-11-09

Axiom 0.9.0 adds persisted system-wide throughput, so the Overview chart is useful beyond the live
five-minute window. It also keeps the post-reboot fixes from 0.8.1.

## System-wide throughput history

- The Overview range picker now offers **5m, 1h, 12h, 24h, 7d and 30d**. Previously every range
  except 5m showed an empty chart because nothing recorded interface traffic.
- **5m stays live.** The desktop samples the active interfaces every second and plots that window
  exactly as before, including the upload and download counters at the top of the page.
- **Longer ranges come from the service.** The Axiom service samples the same interface counters
  once per second, accumulates them into one-minute buckets and stores byte totals in the local
  SQLite history (`throughput_buckets`). A new `traffic.history` pipe command aggregates those rows
  into 1-minute (1h), 5-minute (12h, 24h), 1-hour (7d) or 6-hour (30d) points.
- **Measured rates, not guesses.** A point is bytes divided by the seconds actually observed in its
  bucket. A bucket with no measurement stays a gap, so a chart never shows a flat zero for a period
  the service was not running.
- **Bounded and local.** One row per minute is about 1,440 rows and a few hundred KB per day; the
  existing 30-day retention removes older rows together with the flow history. Only byte totals are
  stored - no payload, host, DNS or per-app content.
- **Clear failures.** Without the service, selecting a longer range states that history is
  unavailable and why. An open historical range refreshes every 30 seconds; switching back to 5m
  restores the live series immediately.

## Verification

- `dotnet build Axiom.sln`: 0 warnings, 0 errors.
- `dotnet test Axiom.sln`: 439 passed, 0 failed. Added coverage for the throughput schema migration,
  minute/bucket aggregation with explicit gaps, retention, the traffic-engine history contract, and
  the Overview page with both a working and an offline service client.
- Installed the new service and desktop on Windows 11 and queried the live pipe:
  - `traffic.history` for 30m returned 31 minute points with a measured bucket;
  - the same query for 12h returned 145 five-minute points;
  - both carried the detail that history starts when the service first ran.

## Known limitations

- History starts when the service first runs. A fresh install shows a gap for the time before it;
  the chart fills in as the service records minutes.
- Values are system-wide interface counters. Per-application byte history still comes from TCP
  extended statistics only, so UDP-only applications keep their existing "traffic not measured"
  state.
- ETW telemetry is not integrated yet; SNI, TLS certificate subjects, DNS query names and exact
  per-connection byte counts remain missing evidence.
- No reputation or threat-intelligence feed is configured; Axiom does not invent a score.
