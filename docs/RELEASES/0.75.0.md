# Axiom 0.75.0

**Released:** 16 November 2026

## OS enforcement policy, provisioned by the service

0.74.0 shipped the provisioner, but the installer runs unelevated for that step, so the write to
`%ProgramData%\Axiom\enforcement-policy.json` failed silently and `enforcement.status` still reported
`enabled=false` with zero rules. Verified on a fresh 0.74.0 install: `policy=False`.

The service now provisions its own policy on the first status request (it runs as LocalSystem, so it
can write ProgramData):

- `EnforcementPolicyProvisioner.EnsureMachineDefault` discovers local profiles that have a `.ssh`
  store or an Axiom install and writes one policy covering them — the service cannot know which user
  made a request.
- The default still blocks agent reads/writes/deletes under `.ssh`, `.aws`, `.kube`, `.gnupg`,
  `.git-credentials`, `.npmrc`, `Microsoft\Credentials` and the Chrome profile for the eleven
  harnesses, and keeps `protectSelectedOperations` elsewhere.
- An existing operator policy is never overwritten; the scope list is capped so the rule count stays
  under the validator's 512 bound.
- The installer message no longer claims "existing policy kept" when the write simply lacked
  elevation.

## Verification

- `dotnet build Axiom.sln -c Release` — 0 warnings, 0 errors; full suite green before packaging.
- Installed in the lab VM and on the host; `enforcement.status` returns `enabled=true` with agents,
  rules and protected resources, and `%ProgramData%\Axiom\enforcement-policy.json` exists.
