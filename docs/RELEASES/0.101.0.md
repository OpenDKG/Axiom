# Axiom 0.101.0

**Released:** 17 November 2026

## Axiom no longer asks you to block Axiom itself

The Shield "New outbound applications" list was filtering Windows and Microsoft-signed binaries,
but not Axiom's own executables. On a normal install that put `Axiom.Desktop.exe` and
`Axiom.Service.exe` in the ask list, and on a Complete install the Blackbox/DKG runtime under
Axiom's module directory could appear too. A user could then block the agent-security tool they
were configuring, or at best had to dismiss it.

- `ShieldProcessFilter` now treats Axiom's own install roots as trusted and never prompts for them:
  `%LOCALAPPDATA%\Programs\Axiom`, `%LOCALAPPDATA%\Axiom` (modules and their runtimes),
  `%ProgramFiles%\Axiom` and `%ProgramFiles(x86)%\Axiom`.
- The explanation under the list now says "N trusted process(es) are not prompted (Windows,
  Microsoft-signed or Axiom's own)."
- Unrelated user paths and unsigned third-party executables are still prompted; the filter only
  adds Axiom's own roots. Nothing is blocked or unblocked by this change.

## Verification

- `dotnet build Axiom.sln -c Release` — 0 warnings, 0 errors.
- New `ShieldProcessFilterTests`: Axiom desktop/module/service paths are ignored, unrelated user
  paths and empty input are still prompted.
- Windows CI build, tests and packaging check pass; 0.101.0 installed on host and in the VM.

## Note

The lab's DKG node runs from `C:\Lab\tools\node-...`, which is not an Axiom install root, so a lab
run can still show that path as pending. A normal Complete install keeps the runtime under
`%LOCALAPPDATA%\Axiom` and is covered.
