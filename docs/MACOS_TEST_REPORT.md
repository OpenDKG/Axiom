## Fixes made during F–H

- DNS restore after disable could log `restore check …: unreadable` and leave system DNS at 127.0.0.1 (seen once when the daemon was running from a replaced bundle). The configurator now retries reads, restores services listed in the backup even when unreadable, and keeps the backup until the state is known. The dev deploy script did not actually restart the daemon (escaped `&&` in the remote command); fixed.
- No false "Privacy Shield DNS is not answering" alert during a normal disable on macOS (8 s grace while the daemon restores DNS).
- macOS wording for system DNS on Privacy Shield and Support (no "UAC/adapter helper" text), Applications/Firewall write prompts no longer mention an "isolated test VM" off Windows.
- Axiom's own daemon (`Axiom.app/Contents/Resources/service/axiomd`) is no longer listed as a new outbound application waiting for Block/Allow.

## Known limitations

- Tested only in an Intel (x86_64) VM; Apple silicon (`osx-arm64`) is built but untested.
- Ad hoc signed with SIP off and developer mode on; Developer ID signing, provisioning profiles and notarization need an Apple Developer team with the Network Extension capability.
- `osascript -e 'quit app "Axiom"'` reports -128 (User canceled) although the app quits (Avalonia terminate reply).
- ICMP is not filterable (the content filter sees TCP/UDP socket flows only).
- Enabling, disabling or upgrading the filter drops TCP connections that were established while it was active (macOS behaviour).
- Ad hoc (development) builds: every upgrade of the extension re-shows the "Filter Network Content" prompt because the filter configuration is re-created (its code-signing requirement pins the ad hoc cdhash). Developer ID builds are not affected.
- App Translocation defeats `appPath` rules for quarantined apps launched outside `/Applications` (ARCHITECTURE §3.1).
- Blocked TCP connections fail with a connect timeout, not a reset.
- Privacy Shield redirects enabled services whose interface is active plus services with no known device/status (conservative); all are restored on disable.
- Agent protection config paths are assumed to be the same as the Windows equivalents under `~`; they were not individually verified on macOS.
- The optional DKG and Blackbox installers are PowerShell-only and not available on macOS (the Agents page shows them as not running).

## Windows runner

`Axiom.Infrastructure.MacOS.Tests` and `Axiom.Desktop.Avalonia.MacOS.Tests` exercise macOS-only runtime behaviour
(`/` path expectations, `File.SetUnixFileMode`, launchd/sysext wording, `desktop.lock` cleanup) and went red on the
Windows 11 VM run (`docs/WINDOWS_REGRESSION_2026-11-12.md`, 12 + 1 failures) without any Windows code being involved.
Both csproj files now set `<IsTestProject Condition="$([MSBuild]::IsOSPlatform('Windows'))">false</IsTestProject>`:
the projects still compile on every OS, but `dotnet test Axiom.sln` on a Windows runner no longer executes them
(verified on Linux by inverting the condition to `IsOSPlatform('Linux')`: the two assemblies disappear from the
solution test run). The two `MacBundleLayoutTests` cases in `Axiom.Presentation.Tests` that compared `Path.Combine`
output against literal `/` strings now build their expectations with `Path.Combine`, and
`FilterEnforcementSummaryTests.Firewall_page_requeries_enforcement_when_stale` derives its "now" from
`FirewallPageViewModel.LastEnforcementRefreshUtc` instead of the wall clock (no `Task.Delay`), so it cannot flake
under load. Not re-run on the Windows VM in this pass.
